# CW Foundation v1.0

- Owner: Alaa Elsayed and Mo Ashour. Date: 08-Sep-2026.
- Purpose: the standing method for building the Commercial Workbench in Claude Code. The product is defined in docs/plan/CW_02_Blueprint_v0.md; the schedule in docs/STAGES.md; decisions in docs/DECISIONS.md. This document changes only when a decision in DECISIONS.md is formally reopened.

## 1. What this replaces, and why it is better

| Old method (chat era) | CW method (Claude Code) | Why |
|---|---|---|
| Empty container each chat; up to 20 files re-attached; SHA256 pin on every file | The repository persists; git is the pin; a clean tree on a tagged `main` is the gate | Hashes existed because files had to be re-uploaded. Git makes them unnecessary |
| Step MD per chat with a file manifest | Stage file per session in docs/stages/; no manifests | The repo is the manifest |
| Audit script producing a deterministic record JSON | pytest suite plus a read-only auditor subagent; determinism proven by a test that runs an export twice and compares bytes | Same guarantee, native tooling, re-run in seconds |
| Foundation v2.5 plus six delta documents, then a consolidation | DECISIONS.md edited in place with dated lines; git history is the delta chain | One register, no reconciliation step |
| Thirteen-section Foundation restated in every chat | CLAUDE.md under 150 lines, loaded automatically every session | Claude Code reads it without being asked |
| Hygiene checked by the audit after the fact | Hygiene is a test that fails the build | Cannot ship a violation |
| One step, one chat, twenty-five tool calls | One stage, one session, one branch | Bigger safe unit, same boundary discipline |

Kept unchanged because it worked: locked decisions with IDs; one stage at a time; the audit never edits the build; no finding is silently resolved; steer by fixing the stage file; stop and say so when a decision does not fit; present each deliverable when it passes; a CMD run block and a Codex review brief with every stage; two handover sets at the end.

## 2. The stage protocol (every stage, no exceptions)

1. Open: new terminal, `claude`, type `/stage Snn`. Claude reads CLAUDE.md, this file, DECISIONS.md, the stage file and the previous handover; restates objective, decisions touched, acceptance tests; enters plan mode; you approve the plan.
2. Gate: `git status` clean on `main`; `pytest` green; `python manage.py check` green; branch `stage/Snn` created. A red gate halts the stage - diagnose, fix on main through its own mini-stage, retry.
3. Build: small commits with plain messages (`S07: raise-variation form`). Tests named in the stage file are written before or with the code. Each deliverable is presented when it passes its own check.
4. Audit: `/audit Snn`. The auditor subagent has no write tools. It runs the tests, checks each acceptance criterion, checks hygiene and the CLAUDE.md rules, and writes handovers/Snn_audit.md with findings classified BLOCKER, DEFECT or OBSERVATION. It never edits code.
5. Fix: DEFECTs and BLOCKERs are fixed in the build, each recorded in docs/FINDINGS.md with its closure. OBSERVATIONs are recorded and may stay open.
6. Close: `/close Snn`. Tests green; merge `stage/Snn` into `main`; tag `Snn-done`; write handovers/Snn_handover.md (delivered, decisions touched, findings, other-face needs, next stage, CMD run block, Codex brief pointer); update docs/STAGES.md status. End the session. The next stage starts in a new session.

## 3. Determinism and audit doctrine

- Every export is generated by one code path and re-runs byte-identical from the same inputs (a test does this with a frozen clock).
- Every fixture figure used in a test is derived from the fixture file, never typed from memory.
- The audit runs on a scratch database; the working tree is byte-unchanged after any audit run.
- An audit bug belongs to the audit: fix the test, record it as an audit-side finding.
- A locked decision that does not fit the stage stops the stage; it is reopened in DECISIONS.md with a dated line, never worked around.

## 4. Session size

- A stage is one module face or one bounded slice of it; target under 1,500 new lines including tests. If a session grows heavy, `/compact`; if the stage will not close in the session, split it in the stage file (`S07a`, `S07b`), never in the code.
- Never load docs/plan/ files into context unless the stage file names them; CLAUDE.md and the stage file carry what the session needs.

## 5. Handover sets (delivered at S29)

- End-user set: the hosted application URL, the one-page guide per role, the support routine.
- Developer set: the repository at the tagged release, the run-book, the fixture set, the stage files and handovers, docs/plan/.
